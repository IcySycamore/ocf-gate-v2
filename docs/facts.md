# Facts：状态机记住什么

本文只回答一件事：**状态机在运行中需要记住哪些信息，每一组什么时候产生、什么时候清掉。**

设计判据只有一条：

> **一个字段必须至少有一个读者**——一道门、一段逻辑、或一次人类决策。没有读者的字段是文档，不是机制，直接删。

代码位置：[abstract_fact.py](../state_machine/abstract_fact.py)（机制）、[intake_gate.py](../state_machine/intake_gate.py)、[plan_gate.py](../state_machine/plan_gate.py)（形状）。

## 为什么先分两类

把两类东西混在一个类里，混了之后"什么时候能清"就没法机械判断。

|  | 控制状态 | 工作事实 |
|---|---|---|
| 谁产生 | 机器（转移、消耗、校验的产物） | 人和 agent 一起填 |
| 回答的问题 | "现在能不能动" | "要做什么" |
| 例子 | `state`、`approval`、`quota` | `goal`、计划的 Files |
| 寿命 | 整个回合，进 `READY` 清零 | 分组不同，见第 5 节 |

现在落地的只有工作事实那一半（`IntakeFact` / `PlanFact`）；控制状态还留在 [base_gate.py](../state_machine/base_gate.py) 的 `BaseFact` 里，见第 1 节。

## 1. 控制状态

| 字段 | 值域 | 谁写 | 谁读 | 寿命 |
|---|---|---|---|---|
| `state` | 六个状态 | 转移逻辑 | 所有门 | 永久，进 `READY` 重置为 `READY` |
| `approval` | `NONE` / `APPROVE` | `approve` / `consume` / `reject` | 转移表裁决 | 回合 |
| `quota` | 整数 ≥ 0 | 同上 | `PLANNING -> EXECUTING` | 回合 |
| `error_counter` | 整数 ≥ 0 | 命令失败的计数逻辑 | `EXECUTING -> BLOCKED` 的上限规则 | 回合（也可每次离开 `EXECUTING` 归零） |
| `blocked_reason` | 非空字符串 | `block` / `reject_block` | 人类解除阻塞时看 | 阻塞期间，解除时清空 |
| `blocked_by` | `human` / `agent` | 同上 | 审计 | 同上 |
| `unblock_evidence` | 字符串 | agent 的 `request_unblock` | 人类解除时看 | 同上 |

不变量：**`approval is NONE` 当且仅当 `quota == 0`。** 任何分支上只改其中一个都会破坏它。

## 2. 事实类的机制

受理组和计划组共用三个方法，它们在 `AbstractFact` 里，子类只声明字段和规则数组：

| 方法 | 做什么 |
|---|---|
| `update(path)` | 从文本文件**增量**读入：只覆盖文件里出现的键 |
| `validate()` | 按规则数组校验，返回 `(是否通过, 未通过的字段名)`，名字按字段声明顺序 |
| `reset()` | 所有字段恢复默认值：计数归零，字符串清空 |
| `explain(names)` | 把 `validate()` 给的字段名变成给人看的一句话（用规则里的 `why`） |

规则数组长这样，一条规则一个字段：

```python
Rule("goal")                                  # 必填，非空就算过
Rule("reference", required=False)             # 不检查
Rule("grill_rounds", ok=lambda f: f.grill_rounds >= 1,
     why="至少盘问 1 轮")                       # 必填，且要满足条件
```

`ok` 收到的是**整个事实实例**，所以条件可以跨字段（计划组就靠这个表达"给了计划文件就必须有 Steps"）。

三条约定：

1. **每个字段都必须有普通默认值。** 默认值同时是"重置之后的值"，也是从文本读入时推断类型的依据：默认值是 `int` 就按 `int` 读。没有默认值的字段在 `reset()` 时报错。
2. **规则数组必须逐个覆盖字段。** 数目或名字对不上都抛 `RuleMismatch`——漏一条规则等于那道检查静默失效。注意只比数目不够：数目一样而名字写错（`consenus` 写成 `consensus`）照样漏检，所以比的是**字段集合**。
3. **两种失败必须分开。**
   - 规则数组和字段对不上 → **抛异常**。这是程序写错了，不是这次校验失败。
   - 必填项为空或条件不满足 → **返回 `False` 加字段名**。这是"人类还没说清楚"，是正常状态。

   两者都返回 `False` 会让"配置漏了一项"和"人类还没说"长得一模一样，于是前者永远查不出来。

### 事实文件

一行一个 `key=value`，`#` 开头的行和空行跳过：

```
# 受理记录
goal=重构状态机
grill_rounds=2
```

- **顺序无关、可增量写。** 受理是边问边记的，一次记一项。按行号取值的定长格式做不到增量，还会在加字段、少一行的时候静默错位。
- **文件不存在 = 没有键要更新**，不是错误：刚开一次受理、还没记过东西就是这种状态，缺哪些项交给 `validate()` 报。
- **不认识的键、不成 `key=value` 形状的行、整数读成非数字 → 报错。** 静默跳过的代价是少读一项，而少读一项的表现和"人类还没说清楚"一模一样。
- 值里可以有 `=`（按第一个 `=` 切分）。

## 3. 受理组（`IntakeFact`，`ASKING` 期间）

| 字段 | 类型 | 必填 | 谁写 |
|---|---|---|---|
| `goal` | str | 是 | human 说，agent 记 |
| `tool` | str | 是 | 同上 |
| `deliverable` | str | 是 | 同上 |
| `consenus` | str | 是 | agent 归纳，人类确认 |
| `constraints` | str | 是 | human 说，agent 记 |
| `reference` | str | 否 | 同上 |
| `code_style` | str | 否 | 同上 |
| `design_style` | str | 否 | 同上 |
| `plan_style` | str | 否 | 同上 |
| `grill_style` | str | 否 | 同上 |
| `grill_rounds` | int | 是，且 ≥ 1 | **机器自动 +1**（人类每回话一次） |

必填与否写在 `RULES` 里，不写在字段上：那是策略，会变；字段是形状，不该跟着变。

受理组只在 `ASKING` 期间存在。它的唯一消费者是"进 `PLANNING` 的门"，那道门在离开 `ASKING` 时正好跑完，所以离开即清。

## 4. 计划组（`PlanFact`，`PLANNING` 开始 -> 回合结束）

| 字段 | 类型 | 条件 | 谁写 |
|---|---|---|---|
| `plan_path` | str | 可空；空 = 计划只在对话里 | agent |
| `steps` | str | 给了计划文件就必须有 | agent |
| `files` | str | 给了计划文件就必须有 | agent |
| `p0_count` | str | 必须是 `0`，**空值也算失败** | plan-auditor |
| `stack_env` | str | ≥ 4 字符 | human 声明 |

两个细节：

- **口头计划是合法的默认。** 所以 `steps` / `files` 的条件写成"没有计划文件时放行"，这就是 `ok` 收整个实例的用处。要求一份没人读的文件，是让人类为文档付钱。
- **`p0_count` 用字符串存。** 空 = 还没审，和"审了，结果是 0"是两件事；如果用 `int` 加默认值 `0`，没审就会静默通过——门反而漏了。

`validate()` 只管事实自身的完整性。**"计划的 Files 有没有碰保护清单"不在这里**，因为那需要保护清单作为额外输入，是另一道门。

## 5. 寿命与清理时机

判据：

> **一组事实的寿命 = 从它开始被收集，到"最后一个读它的消费者用完"那一刻。**

按这条推，边界是推出来的，不是拍定的：

| 组 | 开始收集 | 清空 | 为什么是这个时机 |
|---|---|---|---|
| 受理组 | 进 `ASKING`（开一次新受理） | 离开 `ASKING` | 唯一的消费者是"进 `PLANNING` 的门"，它在离开 `ASKING` 时跑完 |
| 计划组 | 进 `PLANNING` | 进 `READY` | 消费者不止门：`EXECUTING` 要照它干活，`REPORTING` 要照它写报告 |
| 控制状态 | 回合开始 | 进 `READY` | 回合边界 |
| 全部 | —— | **`BLOCKED` 两个方向都不清** | 它中断一次协作，而不是开始或结束一次 |

## 6. `ASKING -> READY` 的清理顺序

`ASKING -> READY`（"human 只是询问时"）是唯一一条**同时**触发"关闭受理"和"结束回合"的边。

顺序必须写死：**先关受理，再清回合。** 反了的话，关闭受理时已经没有东西可清，那行审计记录会静默不写——不报错，只是少一条。旧项目踩过这个坑，术语表里有记录。

## 7. 门清单

**门按"要进入的状态"挂，不按边挂。** 一条边一条门会漏（`BLOCKED` 从三个状态进、从两条边出），按目标状态挂则每条进入路径都过同一组门。

| 进入 | 门 | 读哪组 |
|---|---|---|
| `ASKING` | 无 | —— |
| `PLANNING` | `IntakeFact.validate()` | 受理组 |
| `EXECUTING` | `PlanFact.validate()`，再加一道与保护清单的比对（未实现） | 计划组 |
| `REPORTING` | 无 | —— |
| `READY` | 无，但触发清理 | —— |
| `BLOCKED` | 无门 | —— |

**门与参数校验的区别**：门读的是累积的事实、回答"能不能进"；参数校验读的是这次调用的入参。所以"进入 `BLOCKED` 必须给非空理由"是参数校验，不是门。

## 8. 待定

- **受理组的必填/可选是我按旧项目经验定的**（`goal`/`tool`/`deliverable`/`consenus`/`constraints` 必填，其余可空），要你确认。
- **`PlanFact` 的字段也是我推的**（`plan_path`/`steps`/`files`/`p0_count`/`stack_env`），来源是旧项目的计划门；要你确认这份形状。
- **`IntakeFact.consenus` 拼写错了**（应是 `consensus`）。它现在出现在字段、`update()` 的键、规则数组三处，越晚改越贵。
- **与保护清单比对的那道门还没写。** 它需要 `PlanFact` 加一个额外输入（清单），所以不能塞进 `validate()`。
- **人类拒绝的落点。** 在 `PLANNING` 拒绝计划，回 `ASKING`（继续对齐）还是进 `BLOCKED`（冻结）？倾向 `ASKING`：拒绝是日常操作，走 `BLOCKED` 会稀释它的信号，而且解除阻塞是人类专属，等于让同一个人对同一个决定确认两次。
- **`REPORTING` 被拒没有落点。** 表里只有 `REPORTING -> READY`。人类说"报告不对，重做"时无处可去，回 `READY` 等于宣告事情了结，可它没了结。
- **`error_counter` 的上限值与归零时机。** 有上限规则才能进 `BLOCKED`，但上限是多少、什么时候归零还没定。
- **控制状态要不要也挪进这个基类。** 挪了之后"清理"变成两个独立动作，顺序问题（第 6 节）也更容易看清楚。
- **事实文件的路径谁定。** 现在 `update(path)` 由调用方给路径，没有类级默认值。
